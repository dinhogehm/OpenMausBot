The Local VM gives each bot a containerized Linux desktop on the same machine as OpenMausBot. It is useful for browser work, downloads, and repeatable automation that should not run directly on your host desktop.

## Requirements

- Docker Desktop, Docker Engine, or a supported Podman setup
- Enough local memory and disk for the desktop image
- A healthy container runtime available to the OpenMausBot process

On Windows, Podman is the preferred Local VM runtime. OpenMausBot checks Podman before Docker and validates the exact Windows-to-VM workspace mount before reusing a container.

Before starting two desktops on Windows, confirm the Podman machine is running and has enough shared CPU, memory, and disk for both. Podman Desktop exposes that machine under **Settings → Resources**; both OpenMausBot desktops consume the same machine budget.

## Run two bot desktops

1. Open **App Settings → Local VM**, prepare the managed desktop image, and choose **Per bot**.
2. Set **Maximum per-bot desktops** to `2`.
3. Give two bots **Local VM** as their computer and create each desktop from that bot's Computer panel.
4. Choose **Open two desktops** from either bot to watch both in one workspace.

Both desktops may keep running, but only one pane can hold interactive control at a time. Switching control releases the previous pane first; opening the two-up workspace never creates or starts a VM.

The equivalent source configuration is:

```json
{
  "localVm": {
    "mode": "per-bot",
    "maxInstances": 2
  }
}
```

Local VMs always run on the same physical host as the OpenMausBot desktop process. `maxInstances: 2` does not pool one VM from a Mac and another from a Windows PC. To use Windows capacity today, run OpenMausBot on Windows with its supported Podman lane and create both per-bot desktops there. The BYO-VPS backend is limited to an x86_64 Linux Docker host; do not point it at Windows as a substitute remote Local VM. Cross-host Mac and Windows pooling is tracked in [issue #508](https://github.com/milind-soni/OpenMausBot/issues/508).

## Persistence

The bot's workspace and browser profile live in a durable mounted directory. Recreating the desktop can repair stale runtime state without deleting the durable workspace.

The desktop's browser is Firefox ESR. Its profile (`~/.mozilla`, with the sites you signed in to, their cookies and sessions) is linked into the durable folder at `workspace/.browser-profiles/mozilla`, so a desktop that is stopped, recreated or upgraded starts with the same signed-in Firefox. Sign in once per bot desktop (from a **Sign in needed** card, or **Take control** in the Computer panel) and it stays signed in until the site itself ends the session.

Desktops created before this layout kept Firefox inside the container. Before OpenMausBot removes one of them (to recreate or upgrade it), it copies that `~/.mozilla` into the durable folder, unless a durable Firefox profile is already there, and it removes nothing if the copy fails. Other profiles a bot created in `.browser-profiles` (such as `firefox-qa`) are left as they are. Deleting the bot deletes its folder, profile included.

The durable folder holds live sign-in cookies, so treat it like a password: it stays in the OpenMausBot data folder with owner-only permissions, and browser profiles are never included in a workspace backup or export.

## Saved logins

A bot on a Local VM can sign in with a [saved login](/docs/security/permissions-and-secrets#saved-logins) or one from a connected 1Password vault: on the site's login page in the desktop's Firefox it calls `fill_login`. OpenMausBot reads the address of the page in Firefox's front window through the desktop's accessibility service, and fills only over https and only on that login's own site or the sign-in hosts saved with it (a login kept to **Only on this exact address** fills on that host alone). It does not submit the form: the bot presses the sign-in button, and on a two-step login calls `fill_login` again for the next step. It focuses the username, password and one-time-code boxes it finds there and types the values as key presses through the desktop's input driver. The password goes from OpenMausBot straight to that driver: it is not put on a command line, in a log, in the bot's conversation or in the bot's shell output. If the page changes site, you take control, or a character cannot be typed on the desktop's keyboard (some accented letters or symbols), it stops, empties what it typed, and the bot asks you to sign in instead.

Keep in mind that the bot runs its own commands on the same desktop, so it could in principle watch that desktop's keyboard or screen while a login is typed; give a Local VM bot only logins you would trust it with. Desktops made before this release need **Prepare** in **App Settings → Local VM** and a recreate before `fill_login` works there.

## Ownership and reuse

Local VM ownership uses a renewable lease. OpenMausBot validates the resolved image and container safety contract before reuse instead of trusting only a mutable image tag.
