# Autonomous 24/7 — what changed, per item

Status: living document for the "desenvolvimento contínuo autônomo 24/7" initiative
(Sep 7, 2026). One section per work item; each says what changed, why, how to
verify it, and what was deliberately left out.

## a-unattended-approvals — a workflow node never waits on a click

Branch `feat/a-unattended-approvals`.

### The problem

The live pipeline ("Entrega contínua · nuria-platform", 11 agent nodes on Codex
bots, 09:00 on weekdays) never got past its first node in five days. Every
attempt opened a permission card (`session_search`, `shell gh project
item-list …`) that nobody was there to click; the card stayed open until the
node's `timeoutMinutes` (15 min) ran out, three times over, and the run failed
with "node timed out" — a receipt that says WHEN it died, not WHY. On top of
that, the third attempt's cards carried `approvalScope: "local-computer"`,
which no remembered grant may answer at all.

### What changed

**1. Fail-fast denial on workflow turns** (`server/workflow-unattended-card.ts`
`denyUnattendedWorkflowCard`, called from the `request.opened` fold in
`server/index.ts` with every side effect injected; `server/auto-approve.ts`
`unattendedDenial`).
On a turn whose dispatch was a workflow node (`automationSource: "workflow"`),
a permission request that `autoVerdict` cannot answer is DENIED by the harness
instead of parked on a human. The card is still written to the node's
transcript (title "Denied unattended"), with one free-text `held` line that
names the tool, what it asked, the exact grant key that would have covered it,
the scope, and the rule that decided, e.g.

    denied unattended: shell "/bin/zsh -lc \"gh project item-list 10 --owner @me\"" (key shell:gh) — no always-allow names "shell:gh"

The same line goes to the decision log (`decision: "auto-denied"`, new
`DecisionKind`) and to the engine (`WorkflowEngine.noteDenial`). Questions,
and turns a person / a webhook / a room started, are untouched.

Grace: `OMB_WORKFLOW_DENY_GRACE_MS` (default 0, capped at 10 min). With a
grace the card is titled "Approval needed", the person is notified, and the
harness denies only if nobody answered within the window.

If the denial cannot be delivered (provider gone, ask already settled) the
card stays open with a note saying so, the bot is marked waiting-on-you and
the person is notified as for an ordinary card, and the node timeout is the
backstop it always was. The engine and the audit log learn of a denial only
once the provider took it; a person's click that lands while the answer is
in flight is never overwritten (the card is re-read before it is patched).

The bot is told what it MAY use, not what was refused: the Codex driver
answers a denied permission with a bare decline and discards the harness's
note, so `_buildNodePrompt` lists the effective keys (bot ∪ node, via the new
`botGrants` engine option) and says a denial carries no explanation;
`WORKFLOW_PROMPT` says the same and points at the node prompt. The listed
keys are `unattendedHonoredGrants(bot, node)`: the union minus everything
the verdict would refuse on that turn (desktop scope, command keys with no
program or a shell for one, blind edit keys not declared by the node), so
the prompt never promises a key that ends in a denial.

**2. Per-node allowlist** (`shared/workflow.ts`, `server/workflow-api.ts`,
`server/workflow-run.ts`, `server/index.ts`, `src/components/WorkflowNodePanel.tsx`,
`src/lib/workflow-capabilities.ts`).
Agent nodes carry an optional `alwaysAllow?: string[]` in the same vocabulary
as `bot.alwaysAllow` (`Bash:gh`, `shell:gh`, `session_search`). The validator
flags blanks, padding, repeats and non-lists as `bad-always-allow` (error,
gates a run like every other error); the API pins only the shape (list of
strings, ≤200). The engine passes the node's list to the harness on every
dispatch and re-prompt (`startTurn(…, turn: { alwaysAllow })`), the harness
records it per thread, and the fold judges the request under
`effectiveAlwaysAllow(bot, node)` — the union, bot entries first — with the
existing unattended rules unchanged: a node can name MORE programs, never
broader ones (bare shells, the desktop and the guards are still refused). The
node panel gets a "Pre-approved tools on this node" textarea, one key per
line; the run timeline paints each recorded denial in red under the step.

Two related fixes that the allowlist would have been useless without:

- `namedNarrowly` in `autoVerdict` read EVERY keyless grant as an unnameable
  shell, so `session_search` in a bot's always-allow could never fire
  unattended. The widening is scoped to WORKFLOW turns only (the fold passes
  `workflowGrants`, the node's own keys): there, an ordinary tool's key names
  one thing and fires; a command tool whose key collapsed to the bare tool is
  still refused; and a blind file-edit grant (`edit`, `fileChange` — the card
  carries no path, so the sensitive guard cannot see it) fires only when the
  NODE declared it, never off the bot's list alone. A webhook turn keeps the
  older rule unchanged.
- `WorkflowNodeResult.denials?: string[]` (optional; old receipts load
  unchanged). Denials are carried across a node's attempts (timeout, retry)
  and land on the node's result — on success ("the bot worked around it this
  time"), on the drawn `failed` edge (summary becomes
  `node timed out — denied unattended: …`), and in `run.error` / the failure
  notification when there is no failed edge. The next node's prompt therefore
  names the grant the previous one lacked.

**3. Local-computer scope on a re-dispatch** (`server/turn-provenance.ts`
`turnProvenanceFor`, `server/index.ts` `turnProvenanceByThread`).

What was verified, in code, for the reported sequence (attempt 2 at 09:19
opened cards with `approvalScope: null`; attempt 3 at 09:36 — the engine's
re-dispatch two minutes after the 15-minute timeout — opened cards with
`approvalScope: "local-computer"`):

- The only two ways `integrations.localComputer` gets `scope: "local-computer"`
  are the explicit `bot.computer === "local"` branch and the macOS Auto
  fallback, both via `readCuaConnection()`. The Codex driver tags every card
  from `turn.integrations.localComputer.scope`, per turn, per thread.
- The Auto fallback was gated on `isUnattended(bot.id)` — the per-bot mark —
  which `startTurn` sets synchronously (`markUnattended`) before the mount
  decision in the same call. Within one dispatch nothing observed can clear
  it: a person's `startTurn` on a busy bot throws 409 before its clear; the
  steer route's clear (`auth.kind === "session"`) needs `adapter.steer`, which
  the Codex driver does not implement; the TTL only ages out an IDLE bot.
- Timing matches the engine exactly (09:19 + 15 min timeout + 2 min backoff =
  09:36), so attempt 3 is the engine's dispatch, not a person's.
- Not reproduced from code alone. Two adjacent paths were found on the way:
  (a) a person's message queued on the node's thread while it ran drains
  after the interrupt as an ATTENDED turn (`drainQueuedSends` → plain
  `startTurn`, which clears the bot mark and, on macOS Auto, mounts the
  desktop on the workflow's own task thread) — by then the engine has
  forgotten the thread, so this is a person's turn on that task and is left
  as is; (b) a connector/credential card answered on a node's thread resumes
  it via `cardContinuation` with no unattended opt — after 30 idle minutes the
  bot mark has expired and that resume ran attended. (b) is closed below: a
  continuation inherits the record of the turn it resumes. Whether the live
  build at 09:36 predates the Sep 2 guard (`36219738`) could not be checked
  from here.

The fix moves the decision off the mutable per-bot mark and computes it
ONCE: `turnProvenanceFor(opts, inherited)` (`server/turn-provenance.ts`)
derives `unattended` from the dispatch's own opts — `webhook` and `workflow`
sources and an inherited `unattended: true` are unattended; a routine,
scheduled or Run now, and a person's turn are attended (a routine's prompt
is the person's own text, the decision Auto mode was switched on for;
upstream restricted the mark to webhooks deliberately) — and
`startTurn` writes that record per THREAD (`turnProvenanceByThread`),
synchronously, before any await; a `cardContinuation` inherits the record of
the turn it resumes. The same field now drives the bot mark
(`markUnattended`), the Auto desktop fallback, `approvalModeForTurn` (the Ask
downgrade before the provider spawns) and the `request.opened` fold, all
through `isUnattendedTurn(botId, threadId)` = `unattendedByEither(record,
mark)`, thread record OR bot mark — never narrower than before, so nothing
that asked a human now asks a bot. Room turns (`startGroupTurn`) are
untouched.

Where each behaviour is pinned:

- `server/workflow-unattended-card.test.ts` — the fold's decision, all four
  ways: delivered; undeliverable (card open with a note, card-shown row,
  human notified); grace answered by a person; grace expiring — plus the
  in-flight click race and a vanished card.
- `server/turn-provenance.test.ts` — one unattended answer per source
  (`manual` and `schedule` attended, `webhook`/`workflow` not), continuation
  inheritance, `unattendedByEither`, and the timeout → re-dispatch sequence
  never mounting the desktop.
- `server/auto-approve.test.ts` — webhook keeps the older rule; workflow
  turns fire ordinary-tool grants; blind `edit` fires only off the node;
  `effectiveAlwaysAllow` (union; node cannot widen); `unattendedHonoredGrants`
  (prompt list ⊆ what the verdict honours, checked key by key against
  `autoVerdict`); `unattendedDenial`.
- `server/workflow-run.test.ts` "WorkflowEngine unattended denials" — the
  node prompt lists the effective keys (or says there are none); keys
  reach every dispatch and re-prompt; denials on a finished node; denials
  carried across timeout → interrupt → re-dispatch → failed edge and into the
  successor's prompt; terminal error and notification; cancel forgets.
- `shared/workflow.test.ts`, `server/workflow-api.test.ts` — validation,
  persistence and reload of `alwaysAllow`; `src/lib/workflow-capabilities.test.ts`,
  `src/lib/workflow-graph.test.ts`, `src/state/workflow-reducer.test.ts`,
  `src/components/WorkflowNodePanel.test.ts` — the panel field, the line
  parser, the document diff and the frames.

Manual check on a fixture (never the live app, per `docs/verification`): give a
Codex bot NO grant, run a one-node workflow whose instructions call
`gh project item-list`; the node's transcript shows a "Denied unattended" card
answered within a second, the run reaches its `failed` edge (or fails) inside
the same minute, and the receipt names `key shell:gh`. Add `shell:gh` to the
node's "Pre-approved tools" and re-run: the command runs.

### Left out, on purpose

- No end-to-end test through a live provider: `server/index.test.ts` boots
  the real server against a fake CLI that never raises live permission
  requests. The fold's decision is extracted and unit-tested with every side
  effect injected; what remains in `index.ts` is the binding of those
  effects to the thread, the request and the store.
- Denials are in-memory on the engine: a process restart between a denial and
  the node's result loses that line (the card in the transcript and the
  decision log keep it). Parked denials for pruned or settled runs are
  dropped on the next tick.
- `turnProvenanceByThread` is not pruned on task deletion — one small record
  per thread that ever ran a turn in the process.
- Room turns (`startGroupTurn`) keep the per-bot mark only; the brief asked
  for rooms to be unchanged.
- The grace is process-wide (env), not per node.
