# Autonomous 24/7 — implementation notes

Companion to `2026-09-01-workflow-designer.md` and `2026-09-02-bot-concurrency.md`.
One section per work item of the "desenvolvimento contínuo autônomo 24/7" initiative;
each says what changed, why, how to test it, and what was deliberately left out.

## b-provider-resilience — a provider outage must not kill a run

### Evidence

On 2026-09-03 two runs of "Entrega contínua · nuria-platform" failed with

```
unexpected status 404 Not Found: Unknown error, url: https://chatgpt.com/backend-api/codex/responses, cf-ray: …
```

The node's two retries (`attemptFailure`, linear +60 s / +120 s) were spent in ~3 minutes
and the run took the `failed` edge; the API came back a few minutes later. A third run died
with `exit_before_result` (the engine process exited before answering).

### What changed

**1. Failure classification — `server/workflow-failure.ts` (new, pure).**

What the engine actually has in hand for a failed attempt is NOT one clean message. Read off
the four drivers:

| driver path | `runtime.error` message | `turn.completed` stopReason |
| --- | --- | --- |
| codex `turn/completed` error | — | the provider's text (`unexpected status 404 Not Found: …, url: https://chatgpt.com/backend-api/codex/responses, …`) |
| codex launch-catch (`codex.ts` ~1121) | the provider/transport text (`unexpected status 503 …`), `setup: true` when auth | `rpc_error`, or `auth_required` |
| codex close handler | `codex exited N before turn/completed: <stderr tail>` | `exit_before_result` |
| codex termination | `codex did not shut down after termination was requested` | `shutdown_timeout` |
| claude close handler (`claude.ts` ~1240) | `claude exited N before result: <stderr tail>` — the tail is ANYTHING the CLI printed: `fetch failed`, or `Invalid API key · Please run /login`, or `model not found` | `exit_before_result` (always) |
| claude relaunch-catch | the relaunch error | `exit_before_result` |
| acp close handler | `<kind> exited N before the prompt result: …` | `exit_before_result` |
| acp prompt-catch (`core.ts` ~985) | the error text, `setup: true` when auth | `rpc_error` / `auth_required` |
| acp result error | `Model turn failed: <reason>` or the result's own error | the ACP stop reason |
| pi `turn_end` error (`pi.ts` ~713) | `errorMessage` or `pi turn failed` | `failed` |
| pi spawn error / close | `describeSpawnFailure` text with `setup` / nothing | none |

So `attemptFailure` is fed a **described** line and a class computed from the **pair**:

- `describeWorkflowTurnFailure({ stopReason, message, setup })`: a bare stop code (one
  snake_case token: `exit_before_result`, `rpc_error`, `failed`, …) never stands alone — the
  runtime.error message is the substance and the code is kept in parentheses
  (`claude exited 1 before result: TypeError: fetch failed (exit_before_result)`); a descriptive
  stop reason (codex's provider text) stands as is; nothing at all is
  `the bot did not complete this node`. This line is what lands in `outage.reason`, on the
  failed result and in `run.error`.
- `classifyWorkflowTurnFailure(pair)`: `setup: true` → `other` outright; else the described
  line goes through `classifyWorkflowFailure`.
- `classifyWorkflowFailure(line)`, in precedence order:

| class | rule |
| --- | --- |
| `contention` | "already working" (the harness's 409) — unchanged: re-parked, never charged |
| `capability` | "is not allowed to merge/deploy" — terminal, `failNode` |
| `envelope` | the engine's own "did not produce a valid outcome envelope" |
| `other` (terminal patterns, checked BEFORE any outage rule) | `status/http/error 400/401/403/422`, `401 Unauthorized`, `Invalid API key`, `Missing bearer`, `Not logged in`, `/login`, `invalid request`, `malformed`, `model not found`/`unknown model`/`does not exist for model`, `isn't installed`/`isn't executable`/`ENOENT`/`EACCES`, `quota`/`billing` |
| `provider-outage` | a `404` whose line names a provider backend (`backend-api`, `chatgpt.com`, `openai.com`, `anthropic.com`, `googleapis.com`, `api.x.ai`); 5xx with status context (`status 503`, `HTTP 529`, `502 Bad Gateway`); `429` with status context, `rate limit`, `too many requests`; `overloaded`/`at capacity`; `ECONNRESET`/`ECONNREFUSED`/`ETIMEDOUT`/`ENOTFOUND`/`EAI_AGAIN`/`EPIPE`; `fetch failed`, `socket hang up`, `connection reset/refused`; the drivers' close-handler sentences `exited N before turn/completed | before result | before the prompt result`, `process exited before replying`, `did not shut down` |
| `timeout` | the engine's "node timed out", or `timed out`/`timeout` |
| `other` | everything else — including every bare stop code on its own (`exit_before_result`, `rpc_error`, `failed`, `interrupted`, `spawn_error`) |

Consequences the reviewer reproduced and that are now pinned by tests: a claude CLI death over a
bad key (`… Invalid API key · Please run /login` + `exit_before_result`) is charged to the node,
never waited out; a codex `503 … backend-api …` arriving on `runtime.error` with `rpc_error` IS
an outage; a bare `exit_before_result` with nothing said is `other`.

Why a new module rather than `server/drivers/retry.ts`: that classifier answers "should the
driver relaunch its CLI within one turn" and treats every 404 and every `unexpected status`
as terminal — right for a request the driver just built, wrong for a run that measures in
hours. Why not inside `workflow-run.ts`: 1.2k lines already, and the table tests want a pure
import. The bare-number rules are deliberately conservative ("step 512 failed" is `other`);
a misclassified outage costs up to six hours of waiting, so 5xx/429 require status context.
`BUSY_DISPATCH` moved here so the engine and the classifier share one regexp.

Also exported: `outageDelayMs(attempt, capMs, random)` (60 s × 2^(n−1), capped, ±25 % jitter)
and `outagePlannedAttempts(capMs, horizonMs)` (the "of Z" the UI prints; defaults give 10 in 6 h).

**2. Long backoff without spending attempts — `shared/workflow.ts`, `server/workflow-run.ts`.**

- `Workflow.providerOutage?: { maxBackoffMinutes?: number; horizonHours?: number }`
  (defaults `WORKFLOW_OUTAGE_BACKOFF_CAP_DEFAULT_MIN = 60`, `WORKFLOW_OUTAGE_HORIZON_DEFAULT_H = 6`);
  validated as `bad-numbers`, accepted and clearable (`null`) by the API.
- `WorkflowRun.outage?: { since, until, attempts, of, reason, fallbackBotId? }` — optional, so
  old receipts load unchanged. The wait itself is the run's ordinary `nextAttemptAt`: `dispatchDue`
  re-dispatches it when due and `recoverStranded` leaves it alone (it has a timer), so a restart
  mid-wait needs no special case — this is the design reason for reusing the field.
- `WorkflowRun.currentBotId?: string` — the bot the live dispatch is on. Needed once a
  fallback can hold a node: the timeout sweep, `interruptLiveDispatch`, `activeRunForBot` and the
  envelope re-prompt all address `run.currentBotId ?? node.botId` now, never the canvas bot alone.
- `attemptFailure` classifies first. `provider-outage` → `waitOutOutage`: the run stays `running`,
  `attempt` is untouched, `outage.attempts` increments, `nextAttemptAt = now + delay`. When the
  next slot would land past `outage.until`, the outage is reported spent and the node goes
  **straight** to its `failed` edge / `failNode` with the reason
  `the provider stayed unavailable for Xh (N attempts): <last provider error>` — the linear
  retries are skipped on purpose (two more one-minute retries after six hours of 404s add
  nothing). A non-outage failure after an outage clears `outage` and is charged as usual.
  Contention during an outage re-park keeps the outage. `advance`, `failNode`, `cancelRun` and
  `resumeRun` clear `outage`; a completed node's result never carries it. `outage.until` and
  `outage.of` are recomputed from the workflow's knobs on every outage failure (only `since`
  is fixed), so lengthening the horizon mid-outage is obeyed.
- `workflowOutageWaitMessage(run, formatWhen)` in `shared/workflow.ts` is the one wording:
  "Waiting for the provider: next attempt <when> (attempt Y of Z)". The timeline prints it in
  place of "Retrying at", because nothing of the node's budget is being spent.

**3. Fallback bot on another engine.**

- `AgentNode.fallbackBotId?: string`. `validateWorkflow`: `fallback-same-bot` (error), blank →
  `fallback-missing-bot` (error). `capabilityIssues` (has the roster): `fallback-missing-bot`
  (error) when the lookup returns null, `fallback-missing-capability` (warning) when the fallback
  lacks a `requires` flag — a warning because the engine simply skips it and waits.
- New engine option `botEngine?: (botId) => string | null` (index.ts wires
  `store.bot(id)?.modelSelection.instanceId`). `fallbackEligible`: different bot, both engines
  known and different, `botState === "ready"`, `missingCapabilities(node.requires, …)` empty. An
  engine built without `botEngine` never hands over.
- On the **first** outage failure of the primary, `waitOutOutage` stamps `outage.fallbackBotId`
  and calls `dispatchNode(runId, nodeId, fallbackBotId)` at once — a fresh task on the fallback,
  no attempt charged. Once per outage: if the fallback fails with an outage too, the run enters
  the backoff and every later attempt goes back to the node's own bot (the fallback is a detour,
  not a new home). An ordinary failure on the fallback is charged to the node like any other.
- The 409 race: `fallbackEligible` sees the fallback `ready`, but `startTurn` can still come
  back "already working" (the bot took a turn in between). That contention re-parks the run
  **for the fallback** — `currentBotId` stays on it (`parkedFallbackBot`), so `dispatchDue`
  waits on the fallback's busy state and re-dispatches THERE, and `recoverStranded` re-drives a
  parked or orphaned fallback dispatch on the fallback after a restart. `dispatchNode`'s own busy
  branch keeps the aim too. Without this the reconciler threw the run straight back at the
  dead primary with no backoff and the fallback was never tried again. The timeline says
  "Waiting for fallback bot X to be free (it is busy)" for that state.
- Receipt: a node the fallback finished gets `WorkflowNodeResult.fallback = { botId, because }`;
  the timeline shows "Ran on fallback bot X because: …" on the step and "Running on fallback bot
  X because: …" while it holds the node.
- UI: `WorkflowNodePanel` gains "Fallback bot (other engine)" — every bot but the node's own,
  "None — wait for the provider" first, hidden bots only while bound, a warning when the pick
  shares the primary's engine (`WorkflowPanelBot.engine`, fed from `modelSelection.instanceId`
  by the canvas) or lacks a required capability. Picking "None" drops the key. The hint says the
  fallback runs on its OWN standing permissions (`alwaysAllow`): a workflow turn is unattended,
  so a fallback without e.g. `Bash:gh` always-allowed will card for a human and time out — the
  engine does not copy the primary's grants.
- API: `fallbackBotId: id.optional()` on the agent node schema (blank/padded refused at the door,
  `null` clears); `providerOutage` schema with a `SameKeys` drift guard and in `CLEARABLE_FIELDS`.

### How to test

```
node_modules/.bin/vitest run server/workflow-failure.test.ts     # classification table, backoff math
node_modules/.bin/vitest run server/workflow-outage.test.ts      # engine: entry, progression, horizon, restart, fallback (fake timers)
node_modules/.bin/vitest run shared/workflow.test.ts server/workflow-api.test.ts
node_modules/.bin/vitest run src/components/WorkflowNodePanel.test.ts src/components/WorkflowRunTimeline.test.ts src/state
pnpm typecheck && pnpm lint
```

`workflow-failure.test.ts` has two tables: reason strings, and the (message, stopReason, setup)
pairs per driver path. `workflow-outage.test.ts` ends turns with the same pairs (`failTurn`)
and drives the engine's real 10 s reconciler with `vi.useFakeTimers()`
(`vi.advanceTimersByTimeAsync`), a jitter-free `random: () => 0.5`, and a restart helper that
builds a fresh engine + store over the same files.

Manual check on the real pipeline: set `fallbackBotId` on `codificacao` to a Claude bot,
stop the network for the Codex bot, run — the node should re-dispatch on the Claude bot within
the same second; without a fallback the run should show "Waiting for the provider: next attempt …
(attempt 1 of 10)" and keep `attempt: 0` in `workflow-runs.json`.

### Left out, on purpose

- No canvas UI for `providerOutage` (there is none for `maxNodeExecutions` either); it is
  API/JSON-only for now.
- The fallback is tried once per outage and only from the primary; there is no chain of
  fallbacks and no "prefer the fallback for the rest of the run".
- Auth, request-shape and setup errors are `other`: they retry on the node's budget and are
  never handed to a fallback — a bot with a bad key should fail visibly, not be papered over by
  another bot. A driver that relaunches internally on a transient error (codex/claude
  `turn.retrying`) does so before the engine sees anything; the engine only judges the final
  not-ok turn.
- The claude close handler's stderr tail is 300 chars: a credential error printed earlier than
  that in a long stderr would classify as a plain process death (outage). Not observed; noted.
- `outage.of` is computed on the nominal schedule; jitter can make the real count differ by one.
- The `unexpected status 404` rule needs a provider host in the message. A driver that strips
  the URL would classify the same failure as `other` — the table test pins today's wording.
