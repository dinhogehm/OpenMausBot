# Autonomous 24/7 — what changed, per item

Status: living document for the "desenvolvimento contínuo autônomo 24/7" initiative
(Sep 7, 2026). Companion to `2026-09-01-workflow-designer.md` and
`2026-09-02-bot-concurrency.md`. One section per work item; each says what
changed, why, how to verify it, and what was deliberately left out.

## a-unattended-approvals — a workflow node never waits on a click

Branch `feat/a-unattended-approvals`.

### The problem

The live pipeline ("Entrega contínua · nuria-platform", 11 agent nodes on Codex
bots, 09:00 on weekdays) never got past its first node in five days. Every
attempt opened a permission card (`session_search`, `shell gh project
item-list …`) that nobody was there to click; the card stayed open until the
node's `timeoutMinutes` (15 min) ran out, three times over, and the run failed
with "node timed out" — a receipt that says WHEN it died, not WHY. On top of
that, the third attempt's cards carried `approvalScope: "local-computer"`,
which no remembered grant may answer at all.

### What changed

**1. Fail-fast denial on workflow turns** (`server/workflow-unattended-card.ts`
`denyUnattendedWorkflowCard`, called from the `request.opened` fold in
`server/index.ts` with every side effect injected; `server/auto-approve.ts`
`unattendedDenial`).
On a turn whose dispatch was a workflow node (`automationSource: "workflow"`),
a permission request that `autoVerdict` cannot answer is DENIED by the harness
instead of parked on a human. The card is still written to the node's
transcript (title "Denied unattended"), with one free-text `held` line that
names the tool, what it asked, the exact grant key that would have covered it,
the scope, and the rule that decided, e.g.

    denied unattended: shell "/bin/zsh -lc \"gh project item-list 10 --owner @me\"" (key shell:gh) — no always-allow names "shell:gh"

The same line goes to the decision log (`decision: "auto-denied"`, new
`DecisionKind`) and to the engine (`WorkflowEngine.noteDenial`). Questions,
and turns a person / a webhook / a room started, are untouched.

Grace: `OMB_WORKFLOW_DENY_GRACE_MS` (default 0, capped at 10 min). With a
grace the card is titled "Approval needed", the person is notified, and the
harness denies only if nobody answered within the window.

If the denial cannot be delivered (provider gone, ask already settled) the
card stays open with a note saying so, the bot is marked waiting-on-you and
the person is notified as for an ordinary card, and the node timeout is the
backstop it always was. The engine and the audit log learn of a denial only
once the provider took it; a person's click that lands while the answer is
in flight is never overwritten (the card is re-read before it is patched).

The bot is told what it MAY use, not what was refused: the Codex driver
answers a denied permission with a bare decline and discards the harness's
note, so `_buildNodePrompt` lists the effective keys (bot ∪ node, via the new
`botGrants` engine option) and says a denial carries no explanation;
`WORKFLOW_PROMPT` says the same and points at the node prompt. The listed
keys are `unattendedHonoredGrants(bot, node)`: the union minus everything
the verdict would refuse on that turn (desktop scope, command keys with no
program or a shell for one, blind edit keys not declared by the node), so
the prompt never promises a key that ends in a denial.

**2. Per-node allowlist** (`shared/workflow.ts`, `server/workflow-api.ts`,
`server/workflow-run.ts`, `server/index.ts`, `src/components/WorkflowNodePanel.tsx`,
`src/lib/workflow-capabilities.ts`).
Agent nodes carry an optional `alwaysAllow?: string[]` in the same vocabulary
as `bot.alwaysAllow` (`Bash:gh`, `shell:gh`, `session_search`). The validator
flags blanks, padding, repeats and non-lists as `bad-always-allow` (error,
gates a run like every other error); the API pins only the shape (list of
strings, ≤200). The engine passes the node's list to the harness on every
dispatch and re-prompt (`startTurn(…, turn: { alwaysAllow })`), the harness
records it per thread, and the fold judges the request under
`effectiveAlwaysAllow(bot, node)` — the union, bot entries first — with the
existing unattended rules unchanged: a node can name MORE programs, never
broader ones (bare shells, the desktop and the guards are still refused). The
node panel gets a "Pre-approved tools on this node" textarea, one key per
line; the run timeline paints each recorded denial in red under the step.

Two related fixes that the allowlist would have been useless without:

- `namedNarrowly` in `autoVerdict` read EVERY keyless grant as an unnameable
  shell, so `session_search` in a bot's always-allow could never fire
  unattended. The widening is scoped to WORKFLOW turns only (the fold passes
  `workflowGrants`, the node's own keys): there, an ordinary tool's key names
  one thing and fires; a command tool whose key collapsed to the bare tool is
  still refused; and a blind file-edit grant (`edit`, `fileChange` — the card
  carries no path, so the sensitive guard cannot see it) fires only when the
  NODE declared it, never off the bot's list alone. A webhook turn keeps the
  older rule unchanged.
- `WorkflowNodeResult.denials?: string[]` (optional; old receipts load
  unchanged). Denials are carried across a node's attempts (timeout, retry)
  and land on the node's result — on success ("the bot worked around it this
  time"), on the drawn `failed` edge (summary becomes
  `node timed out — denied unattended: …`), and in `run.error` / the failure
  notification when there is no failed edge. The next node's prompt therefore
  names the grant the previous one lacked.

**3. Local-computer scope on a re-dispatch** (`server/turn-provenance.ts`
`turnProvenanceFor`, `server/index.ts` `turnProvenanceByThread`).

What was verified, in code, for the reported sequence (attempt 2 at 09:19
opened cards with `approvalScope: null`; attempt 3 at 09:36 — the engine's
re-dispatch two minutes after the 15-minute timeout — opened cards with
`approvalScope: "local-computer"`):

- The only two ways `integrations.localComputer` gets `scope: "local-computer"`
  are the explicit `bot.computer === "local"` branch and the macOS Auto
  fallback, both via `readCuaConnection()`. The Codex driver tags every card
  from `turn.integrations.localComputer.scope`, per turn, per thread.
- The Auto fallback was gated on `isUnattended(bot.id)` — the per-bot mark —
  which `startTurn` sets synchronously (`markUnattended`) before the mount
  decision in the same call. Within one dispatch nothing observed can clear
  it: a person's `startTurn` on a busy bot throws 409 before its clear; the
  steer route's clear (`auth.kind === "session"`) needs `adapter.steer`, which
  the Codex driver does not implement; the TTL only ages out an IDLE bot.
- Timing matches the engine exactly (09:19 + 15 min timeout + 2 min backoff =
  09:36), so attempt 3 is the engine's dispatch, not a person's.
- Not reproduced from code alone. Two adjacent paths were found on the way:
  (a) a person's message queued on the node's thread while it ran drains
  after the interrupt as an ATTENDED turn (`drainQueuedSends` → plain
  `startTurn`, which clears the bot mark and, on macOS Auto, mounts the
  desktop on the workflow's own task thread) — by then the engine has
  forgotten the thread, so this is a person's turn on that task and is left
  as is; (b) a connector/credential card answered on a node's thread resumes
  it via `cardContinuation` with no unattended opt — after 30 idle minutes the
  bot mark has expired and that resume ran attended. (b) is closed below: a
  continuation inherits the record of the turn it resumes. Whether the live
  build at 09:36 predates the Sep 2 guard (`36219738`) could not be checked
  from here.

The fix moves the decision off the mutable per-bot mark and computes it
ONCE: `turnProvenanceFor(opts, inherited)` (`server/turn-provenance.ts`)
derives `unattended` from the dispatch's own opts — `webhook` and `workflow`
sources and an inherited `unattended: true` are unattended; a routine,
scheduled or Run now, and a person's turn are attended (a routine's prompt
is the person's own text, the decision Auto mode was switched on for;
upstream restricted the mark to webhooks deliberately) — and
`startTurn` writes that record per THREAD (`turnProvenanceByThread`),
synchronously, before any await; a `cardContinuation` inherits the record of
the turn it resumes. The same field now drives the bot mark
(`markUnattended`), the Auto desktop fallback, `approvalModeForTurn` (the Ask
downgrade before the provider spawns) and the `request.opened` fold, all
through `isUnattendedTurn(botId, threadId)` = `unattendedByEither(record,
mark)`, thread record OR bot mark — never narrower than before, so nothing
that asked a human now asks a bot. Room turns (`startGroupTurn`) are
untouched.

### Left out, on purpose

- No end-to-end test through a live provider: `server/index.test.ts` boots
  the real server against a fake CLI that never raises live permission
  requests. The fold's decision is extracted and unit-tested with every side
  effect injected; what remains in `index.ts` is the binding of those
  effects to the thread, the request and the store.
- Denials are in-memory on the engine: a process restart between a denial and
  the node's result loses that line (the card in the transcript and the
  decision log keep it). Parked denials for pruned or settled runs are
  dropped on the next tick.
- `turnProvenanceByThread` is not pruned on task deletion — one small record
  per thread that ever ran a turn in the process.
- Room turns (`startGroupTurn`) keep the per-bot mark only; the brief asked
  for rooms to be unchanged.
- The grace is process-wide (env), not per node.

## b-provider-resilience — a provider outage must not kill a run

### Evidence

On 2026-09-03 two runs of "Entrega contínua · nuria-platform" failed with

```
unexpected status 404 Not Found: Unknown error, url: https://chatgpt.com/backend-api/codex/responses, cf-ray: …
```

The node's two retries (`attemptFailure`, linear +60 s / +120 s) were spent in ~3 minutes
and the run took the `failed` edge; the API came back a few minutes later. A third run died
with `exit_before_result` (the engine process exited before answering).

### What changed

**1. Failure classification — `server/workflow-failure.ts` (new, pure).**

What the engine actually has in hand for a failed attempt is NOT one clean message. Read off
the four drivers:

| driver path | `runtime.error` message | `turn.completed` stopReason |
| --- | --- | --- |
| codex `turn/completed` error | — | the provider's text (`unexpected status 404 Not Found: …, url: https://chatgpt.com/backend-api/codex/responses, …`) |
| codex launch-catch (`codex.ts` ~1121) | the provider/transport text (`unexpected status 503 …`), `setup: true` when auth | `rpc_error`, or `auth_required` |
| codex close handler | `codex exited N before turn/completed: <stderr tail>` | `exit_before_result` |
| codex termination | `codex did not shut down after termination was requested` | `shutdown_timeout` |
| claude close handler (`claude.ts` ~1240) | `claude exited N before result: <stderr tail>` — the tail is ANYTHING the CLI printed: `fetch failed`, or `Invalid API key · Please run /login`, or `model not found` | `exit_before_result` (always) |
| claude relaunch-catch | the relaunch error | `exit_before_result` |
| acp close handler | `<kind> exited N before the prompt result: …` | `exit_before_result` |
| acp prompt-catch (`core.ts` ~985) | the error text, `setup: true` when auth | `rpc_error` / `auth_required` |
| acp result error | `Model turn failed: <reason>` or the result's own error | the ACP stop reason |
| pi `turn_end` error (`pi.ts` ~713) | `errorMessage` or `pi turn failed` | `failed` |
| pi spawn error / close | `describeSpawnFailure` text with `setup` / nothing | none |

So `attemptFailure` is fed a **described** line and a class computed from the **pair**:

- `describeWorkflowTurnFailure({ stopReason, message, setup })`: a bare stop code (one
  snake_case token: `exit_before_result`, `rpc_error`, `failed`, …) never stands alone — the
  runtime.error message is the substance and the code is kept in parentheses
  (`claude exited 1 before result: TypeError: fetch failed (exit_before_result)`); a descriptive
  stop reason (codex's provider text) stands as is; nothing at all is
  `the bot did not complete this node`. This line is what lands in `outage.reason`, on the
  failed result and in `run.error`.
- `classifyWorkflowTurnFailure(pair)`: `setup: true` → `other` outright; a stop reason that is
  the harness's own stop (`interrupted`, `cancelled`, `aborted`) → `other` whatever
  `runtime.error` was logged earlier (the timeout sweep classifies its own reason as `timeout`
  and forgets the thread before the driver answers the interrupt); else the described line goes
  through `classifyWorkflowFailure`.
- Per-thread `lastRuntimeError` is cleared on every fresh dispatch, on the envelope re-prompt
  (a new turn on the same thread) and when a turn completes ok — codex relays stream errors it
  retries internally (`error` notifications, turn still live), and that message must not
  describe a later turn on the thread.
- `classifyWorkflowFailure(line)`, in precedence order:

| class | rule |
| --- | --- |
| `contention` | "already working" (the harness's 409) — unchanged: re-parked, never charged |
| `capability` | "is not allowed to merge/deploy" — terminal, `failNode` |
| `envelope` | the engine's own "did not produce a valid outcome envelope" |
| `other` (terminal patterns, checked BEFORE any outage rule) | `status/http/error 400/401/403/422`, `401 Unauthorized`, `Invalid API key`, `Missing bearer`, `Not logged in`, `invalid request`, `malformed`, `model not found`/`unknown model`/`does not exist for model`, `isn't installed`/`isn't executable`/`ENOENT`/`EACCES` |
| `other` (account patterns) | `quota`/`billing`/`insufficient_quota`, `/login` — but ONLY when the line carries no 5xx/429 with status context: Gemini's `429 RESOURCE_EXHAUSTED: Quota exceeded` is throttling and is an outage |
| `provider-outage` | a `404` whose line names a provider backend (`backend-api`, `chatgpt.com`, `openai.com`, `anthropic.com`, `googleapis.com`, `api.x.ai`); 5xx with status context (`status 503`, `HTTP 529`, `502 Bad Gateway`); `429` with status context, `rate limit`, `too many requests`, a status followed by an UPPER_CASE reason code (`429 RESOURCE_EXHAUSTED`, `503 UNAVAILABLE`; case-sensitive so "429 tokens" is prose); `overloaded`/`at capacity`; `ECONNRESET`/`ECONNREFUSED`/`ETIMEDOUT`/`ENOTFOUND`/`EAI_AGAIN`/`EPIPE`; `fetch failed`, `socket hang up`, `connection reset/refused`; the drivers' close-handler sentences `exited N before turn/completed | before result | before the prompt result`, `process exited before replying`, `did not shut down` |
| `timeout` | the engine's "node timed out", or `timed out`/`timeout` |
| `other` | everything else — including every bare stop code on its own (`exit_before_result`, `rpc_error`, `failed`, `interrupted`, `spawn_error`) |

Design choice, recorded: **a CLI crash with no explanation of its own is an outage.** The
drivers' close-handler sentences (`codex exited null before turn/completed`,
`claude exited 1 before result` with an empty or uninformative stderr tail) classify as
`provider-outage` — the evidence run of 2026-09-03 died exactly like that when the backend
went away, and a genuine local crash of the CLI will surface a credential, binary or
request-shape message that the terminal patterns catch first. The cost of being wrong is a
wait (bounded by the horizon), not a lost run.

Consequences the reviewer reproduced and that are now pinned by tests: a claude CLI death over a
bad key (`… Invalid API key · Please run /login` + `exit_before_result`) is charged to the node,
never waited out; a codex `503 … backend-api …` arriving on `runtime.error` with `rpc_error` IS
an outage; a bare `exit_before_result` with nothing said is `other`; a stream error codex
retried itself, followed by an ok turn without envelope, a re-prompt and an `interrupted`, is
the node's own failure — never "503 (interrupted)" waited out as an outage.

Why a new module rather than `server/drivers/retry.ts`: that classifier answers "should the
driver relaunch its CLI within one turn" and treats every 404 and every `unexpected status`
as terminal — right for a request the driver just built, wrong for a run that measures in
hours. Why not inside `workflow-run.ts`: 1.2k lines already, and the table tests want a pure
import. The bare-number rules are deliberately conservative ("step 512 failed" is `other`);
a misclassified outage costs up to six hours of waiting, so 5xx/429 require status context.
`BUSY_DISPATCH` moved here so the engine and the classifier share one regexp.

Also exported: `outageDelayMs(attempt, capMs, random)` (60 s × 2^(n−1), capped, ±25 % jitter)
and `outagePlannedAttempts(capMs, horizonMs)` (the "of Z" the UI prints; defaults give 10 in 6 h).

**2. Long backoff without spending attempts — `shared/workflow.ts`, `server/workflow-run.ts`.**

- `Workflow.providerOutage?: { maxBackoffMinutes?: number; horizonHours?: number }`
  (defaults `WORKFLOW_OUTAGE_BACKOFF_CAP_DEFAULT_MIN = 60`, `WORKFLOW_OUTAGE_HORIZON_DEFAULT_H = 6`);
  validated as `bad-numbers`, accepted and clearable (`null`) by the API.
- `WorkflowRun.outage?: { since, until, attempts, of, reason, fallbackBotId? }` — optional, so
  old receipts load unchanged. The wait itself is the run's ordinary `nextAttemptAt`: `dispatchDue`
  re-dispatches it when due and `recoverStranded` leaves it alone (it has a timer), so a restart
  mid-wait needs no special case — this is the design reason for reusing the field.
- `WorkflowRun.currentBotId?: string` — the bot the live dispatch is on. Needed once a
  fallback can hold a node: the timeout sweep, `interruptLiveDispatch`, `activeRunForBot` and the
  envelope re-prompt all address `run.currentBotId ?? node.botId` now, never the canvas bot alone.
- `attemptFailure` classifies first. `provider-outage` → `waitOutOutage`: the run stays `running`,
  `attempt` is untouched, `outage.attempts` increments, `nextAttemptAt = now + delay`. When the
  next slot would land past `outage.until`, the outage is reported spent and the node goes
  **straight** to its `failed` edge / `failNode` with the reason
  `the provider stayed unavailable for Xh (N attempts): <last provider error>` — the linear
  retries are skipped on purpose (two more one-minute retries after six hours of 404s add
  nothing). A non-outage failure after an outage clears `outage` and is charged as usual.
  Contention during an outage re-park keeps the outage. `advance`, `failNode`, `cancelRun` and
  `resumeRun` clear `outage`; a completed node's result never carries it. `outage.until` and
  `outage.of` are recomputed from the workflow's knobs on every outage failure (only `since`
  is fixed), so lengthening the horizon mid-outage is obeyed.
- `workflowOutageWaitMessage(run, formatWhen)` in `shared/workflow.ts` is the one wording:
  "Waiting for the provider: next attempt <when> (attempt Y of Z)". The timeline prints it in
  place of "Retrying at", because nothing of the node's budget is being spent.

**3. Fallback bot on another engine.**

- `AgentNode.fallbackBotId?: string`. `validateWorkflow`: `fallback-same-bot` (error), blank →
  `fallback-missing-bot` (error). `capabilityIssues` (has the roster): `fallback-missing-bot`
  (error) when the lookup returns null, `fallback-missing-capability` (warning) when the fallback
  lacks a `requires` flag — a warning because the engine simply skips it and waits.
- New engine option `botEngine?: (botId) => string | null` (index.ts wires
  `store.bot(id)?.modelSelection.instanceId`). `fallbackEligible`: different bot, both engines
  known and different, `botState === "ready"`, `missingCapabilities(node.requires, …)` empty. An
  engine built without `botEngine` never hands over.
- On the **first** outage failure of the primary, `waitOutOutage` stamps `outage.fallbackBotId`
  and calls `dispatchNode(runId, nodeId, fallbackBotId)` at once — a fresh task on the fallback,
  no attempt charged. Once per outage: if the fallback fails with an outage too, the run enters
  the backoff and every later attempt goes back to the node's own bot (the fallback is a detour,
  not a new home). An ordinary failure on the fallback is charged to the node like any other.
- The 409 race: `fallbackEligible` sees the fallback `ready`, but `startTurn` can still come
  back "already working" (the bot took a turn in between). That contention re-parks the run
  **for the fallback** — `currentBotId` stays on it (`parkedFallbackBot`), so `dispatchDue`
  waits on the fallback's busy state and re-dispatches THERE, and `recoverStranded` re-drives a
  parked or orphaned fallback dispatch on the fallback after a restart. `dispatchNode`'s own busy
  branch keeps the aim too. Without this the reconciler threw the run straight back at the
  dead primary with no backoff and the fallback was never tried again. The timeline says
  "Waiting for fallback bot X to be free (it is busy)" for that state.
- Receipt: a node the fallback finished gets `WorkflowNodeResult.fallback = { botId, because }`;
  the timeline shows "Ran on fallback bot X because: …" on the step and "Running on fallback bot
  X because: …" while it holds the node.
- UI: `WorkflowNodePanel` gains "Fallback bot (other engine)" — every bot but the node's own,
  "None — wait for the provider" first, hidden bots only while bound, a warning when the pick
  shares the primary's engine (`WorkflowPanelBot.engine`, fed from `modelSelection.instanceId`
  by the canvas) or lacks a required capability. Picking "None" drops the key. The hint says the
  fallback runs on its OWN standing permissions (`alwaysAllow`): a workflow turn is unattended,
  so a fallback without e.g. `Bash:gh` always-allowed will card for a human and time out — the
  engine does not copy the primary's grants.
- API: `fallbackBotId: id.optional()` on the agent node schema (blank/padded refused at the door,
  `null` clears); `providerOutage` schema with a `SameKeys` drift guard and in `CLEARABLE_FIELDS`.


pairs per driver path. `workflow-outage.test.ts` ends turns with the same pairs (`failTurn`)
and drives the engine's real 10 s reconciler with `vi.useFakeTimers()`

Manual check on the real pipeline: set `fallbackBotId` on `codificacao` to a Claude bot,
stop the network for the Codex bot, run — the node should re-dispatch on the Claude bot within

### Left out, on purpose

- No canvas UI for `providerOutage` (there is none for `maxNodeExecutions` either); it is
  API/JSON-only for now.
- The fallback is tried once per outage and only from the primary; there is no chain of
  fallbacks and no "prefer the fallback for the rest of the run".
- Auth, request-shape and setup errors are `other`: they retry on the node's budget and are
  never handed to a fallback — a bot with a bad key should fail visibly, not be papered over by
  another bot. A driver that relaunches internally on a transient error (codex/claude
  `turn.retrying`) does so before the engine sees anything; the engine only judges the final
  not-ok turn.
- The claude close handler's stderr tail is 300 chars: a credential error printed earlier than
  that in a long stderr would classify as a plain process death (outage). Not observed; noted.
- `outage.of` is computed on the nominal schedule; jitter can make the real count differ by one.
- The `unexpected status 404` rule needs a provider host in the message. A driver that strips
  the URL would classify the same failure as `other` — the table test pins today's wording.

## c-approval-reach — the human gate is not where the pipeline dies

Branch `feat/c-approval-reach`.

### The problem

Three runs of "Entrega contínua · nuria-platform" reached
`revisao → aguardar-humano → aprovacao-merge`. Two were cancelled by hand;
the third waited the full 24 hours, expired as `rejected` (the default
`onExpire`), and `avisar-falha` threw away a finished PR. The approval card
existed in exactly one place — the run panel on the canvas — and the only
signal outside it was a `workflow-approval` notification that opened the
bot's chat, where there was nothing to click.

### What changed

**1. The gate reaches the person, through the mechanisms that already exist**
(`server/workflow-approval-reach.ts` new, pure; `server/workflow-run.ts`;
`server/index.ts`; `server/workflow-api.ts` `workflowApprovalBotId`).

Not a second notification system. Three existing things, joined:

- *The card.* An ordinary option card with a `requestId`, of the durable,
  harness-owned kind a routine proposal or a profile change already uses —
  no provider request behind it. It carries `tool: "workflow_approval"`
  (what makes both clients treat it as an approval: the decision takes over
  the composer on the desktop, and the companion sends allow/deny), the
  options `Approve` / `Deny`, a `workflowApproval: { runId, workflowId,
  nodeId }` payload, the node's prompt, the previous step's summary and a
  `held` note that says since when the gate waits and what expiry will do.
  `requestId` is `workflow-approval:<runId>:<nodeId>:<approvalRequestedAt>`
  — one per OPENING of the gate, so a cycle through the same node gets a
  fresh card and a stale click on the older one cannot settle the newer
  gate. The card is upserted by request id: a reminder or a re-notification
  rewrites the note and appends one text line under it, never a second
  card.
- *Where.* The chat of the bot that ran the LAST agent step before the gate
  (the reviewer whose summary the card quotes), else the entry node's bot,
  else the general notification pick (`workflowApprovalBotId`, a wrapper
  over `workflowNotificationBotId`). Optionally a room —
  `notifyTargetGroupId` on the node — with the same card signed by the
  workflow author, posted with the same store calls a notify node's post
  makes, and the room marked unread. A room that no longer exists is
  logged, never a failure of the gate: the chat copy and the canvas still
  carry the decision.
- *The buzz.* `notifyUser` unchanged: the same `notify` frame every approval
  card sends, which the desktop shows as an OS notification and the iOS
  companion delivers locally (`Session.swift` → `NotificationCoordinator`).
  The bot picked for the frame is the one the card was posted to, so the
  tap lands on the thread that carries the card. The bot is marked unread
  (badge on both clients). The bot is NOT put on `waiting-on-you`: that
  activity derives `busy: true`, which would block every other turn on an
  idle bot; the existing code only sets it on a bot that is already busy.
- *The decision.* Both respond routes (`/api/bots/:id/respond`,
  `/api/threads/:id/respond`) intercept a `workflowApproval` card FIRST and
  call `resolveWorkflowApprovalCard`, which goes through the engine's own
  `resolveApproval` — the canvas's route — so chat, room and canvas write
  the identical receipt. `allow` → `approved`, `deny` → `rejected`, anything
  else 400. The engine's new `approvalReach.settle` hook then marks every
  recorded copy of the card (`answered: "allow" | "deny"`, the marks the
  clients already render), and the route marks the card in its own thread
  regardless. A card already answered returns 200 `alreadyAnswered` with
  what happened — the second click is a no-op, never an error. A run that
  is gone, moved on, cancelled or waiting on a LATER opening of the same
  gate closes the card as `unavailable` and answers 409. `closeOpenApprovals`
  (a person interrupting the bot) now skips gate cards, like routine and
  skill cards: the gate is owned by the engine, not by any turn.

Engine side: `openApproval` parks the run first (persisted), then
`reachApproval(kind)` — card, then notification, in that order, because the
notification's tap must land on something. The threads that carry the card
are persisted on the run as `approvalThreadIds` the moment they are known,
`[]` included; `settleApproval`, `cancelRun` and `failNode` (a gate edited
away) settle those copies AFTER the receipt is written. A waiting receipt
with NO `approvalThreadIds` — a crash between the park and the post, or a
run that was waiting when the app was upgraded — gets its card (and one
notification) on the next sweep, once. A throwing `announce` is logged and
the gate stays open: the timer, not the card, keeps a run alive.

**2. Expiry that does not discard work** (`shared/workflow.ts`,
`server/workflow-run.ts` `sweepApprovals`).

`onExpire: "approved" | "rejected" | "renotify"`, plus `maxRenotify`
(default 5, 1..30). Under `renotify`, an expired window is RE-ARMED and the
person asked again — card refreshed with "Asked again (n of N)", one text
line in the chat and the room, a fresh `renotify` notification — until the
round count is spent, and only then `rejected` with the summary `expired
without a decision after N re-notifications`. Persisted on the run:
`approvalRenotified` (rounds so far), `approvalRenotifiedAt` (the current
window's start; the expiry and reminder clocks run from
`approvalRenotifiedAt ?? approvalRequestedAt`, while `approvalRequestedAt`
stays the instant the gate OPENED so the receipt's `startedAt` and the
"waiting since" line survive every round), and `approvalNotices` — one
`{ at, kind: "reminder" | "renotify" }` per nudge, copied onto the node's
result as `notices` when the gate settles, so "re-notified 3×, then
approved" is readable after the fact. The re-arm is persisted BEFORE the
reach (a notification that fails is retried by the next round, never by
re-arming every tick). `CLOSED_APPROVAL` is the one place every gate marker
is reset, shared by settle, cancel and terminal failure.

Defaults, deliberately split: a NEW gate from the palette gets
`onExpire: "renotify"` (`createWorkflowNode`,
`WORKFLOW_APPROVAL_ON_EXPIRE_DEFAULT_NEW`); a gate saved WITHOUT the field
keeps the engine's older fallback, `rejected` — existing definitions do not
change behaviour by being loaded.

**3. The halfway reminder** goes through the same reach (card note
refreshed, nudge line, `reminder` notification) — once per WINDOW:
`approvalRemindedAt` resets with every re-notification, so each round gets
its halfway nudge, and each is a `reminder` notice on the receipt.

**4. Validation, API, UI, timeline.**

- `validateWorkflow`: `bad-approval-config` (error) for an `onExpire`
  outside the three, a `maxRenotify` outside 1..30 or not whole, a blank
  `notifyTargetGroupId`. `expiresHours` stays `bad-numbers`. The policy is
  not an outcome: `nodeOutcomes` is still `approved` / `rejected`.
- API schema: `onExpire` is a closed enum at the door (an unknown policy is
  a 400, as before); `maxRenotify: optionalNumber`; `notifyTargetGroupId:
  id.optional()`; all three clear on `null`. `SameKeys` drift guard updated.
- Node panel: **On expiry** — `Route to rejected (unset)`, `Ask again, then
  route to rejected`, `Route to approved`, `Route to rejected`; **Ask again
  up to (times)** appears under renotify and is dropped from the document
  when the policy changes; **Also ask in room** — none first, every room, a
  lost room kept visible as `Missing room <id>`. New gates start on
  renotify.
- Chat card (`ApprovalCard`, `PendingApproval`): a `workflowApproval` card
  reads "<bot>'s workflow needs your decision", takes over the composer as
  a durable request (Approve / Reject, no "cancel turn"), and records
  approved / rejected / "no longer waiting". en + pt-BR strings.
- Timeline: while waiting, `Waiting for a decision since … · <node> ·
  reminder sent at … · re-notified N× (last at …)`; on a settled gate's
  step, `approvalNoticesLine`: `reminder sent at … · re-notified N× (…)`.
- Persisted data: every new field is optional; runs and workflows saved
  before this load unchanged (a waiting run gets its card on the next tick,
  see above).

### Left out, on purpose

  companion app (`ios/Sources/CompanionCore/Models.swift`) maps only

## d-continuous-cycle — the workflow as a continuous cycle, the engine as the valve

### The problem

The user's pipeline ("Entrega contínua · nuria-platform") was a straight line
scheduled once a day at 09:00: `triagem → spec → codificacao → testes-pre →
revisao → (aprovacao-merge → merge) → deploy → testes-prod → doc →
update-canal`, with `sem-demanda` as the terminal node when triage finds
nothing to do. One shot per day means one shot per day at every failure
mode in the brief, and a lap that finishes at 10:00 sits idle until the next
morning. The engine had three things standing in the way of running it
continuously:

1. `triggers.schedule` knew only `daily` and `once`.
2. There was no way to pause a run between laps: an edge back to the entry
   re-dispatches it the instant the last node finishes.
3. `WORKFLOW_MAX_NODE_EXECUTIONS` defaulted to 30 and counted every step,
   and reaching it was always a hard failure.

### What changed

**1. Interval trigger** (`shared/workflow.ts`, `server/workflow-run.ts`,
`server/workflow-interval.ts`, `server/workflow-api.ts`, canvas schedule
editor in `WorkflowCanvas.tsx`).

```ts
schedule: {
  type: "interval",
  minutes: number,                     // whole, >= 5
  activeHours?: {                      // local wall clock
    start: "HH:MM", end: "HH:MM",      // start > end wraps past midnight
    weekdays?: number[],               // 0 = Sunday; absent = every day
  },
}
```

Semantics — the engine is the valve:

- While the workflow has a LIVE run (queued, running, waiting-approval) the
  clock is held at `undefined`: nothing is armed. A manual or webhook run
  therefore pushes the next scheduled run out; it never stacks a queued run
  behind the live one.
- The moment the workflow is idle, the next run is armed at
  `lastRun.endedAt + minutes` (or `now + minutes` if no run is on record —
  which includes a history pruned by the receipt cap), moved to the next
  active-window start when that instant falls outside `activeHours`.
- Firing reuses the tri-state `nextRunAt` and its double-fire guard: the
  clock is set back to `undefined` BEFORE `startRun`. A crash between the two
  leaves an idle workflow with no clock; the next sweep re-arms one interval
  after the last run. A slot skipped, never a run fired twice.
- **No missed-slot receipt for intervals** (`recordMissedRun` is not used).
  A calendar slot can be missed; an interval has no slot to miss — an armed
  instant in the past is simply "due", so a computer that slept fires once
  on waking. Tested: two days late still starts exactly one run and notifies
  nothing.
- A start the engine REFUSES (validation error, revoked capability) leaves
  the same failed receipt a calendar schedule does, via `recordRefusedRun`.
  That receipt ends "now", so the next arm lands one interval later: a
  natural backoff instead of a refusal every 10 s.
- Interval math never goes through the injected routine `nextOccurrence`;
  its option type is now `WorkflowCalendarSchedule` (daily/once only). The
  interval helpers are pure and local-timezone (`withinActiveHours`,
  `nextActiveWindowStart`, `intervalFireAt`).

**2. `wait` node** (`kind: "wait"`, `minutes` 1..1440, single outcome
`elapsed`). `dispatchNode` parks the run: `currentNodeId`, a persisted
`waitUntil`, no task, no thread, no notification. A new `sweepWaits` step in
`tick()` (right after `sweepApprovals`, before anything that dispatches)
advances the run through the ordinary `advance()` path once the instant
passes, recording `{ outcome: "elapsed", summary: "Waited N min" }`.
`isStranded` excludes runs carrying `waitUntil` — without that,
`recoverStranded` would re-dispatch the wait node every tick and push the
instant out forever. Cancel, terminal failure and `advance` all clear the
field. A wait node edited away under a parked run fails the run, like an
orphaned approval gate. `sweepTimeouts` ignores it (no `dispatchedAt`).

**3. Execution cap** — semantics changed, deliberately:

- `WORKFLOW_MAX_NODE_EXECUTIONS` default 30 → **200**; `maxNodeExecutions`
  validated in **1..1000** (`bad-numbers`).
- The counter now counts **bot work only**: `agent` and `approval` results
  (`countsTowardExecutionCap`). `wait` and `notify` steps are free — they
  cost nothing and cannot run away on their own, and counting them would
  make a slow cycle pay for pausing. A result whose node was since deleted
  still counts (a safety net must not widen when it cannot classify).
- The check runs only when bot work is about to be dispatched, so a notify
  or wait AFTER the last allowed agent step still executes (a cycle's
  closing notification is never the step the cap swallows).
- **What happens at the cap.** `follow()` brought the run along an edge, so
  the last node was not a sink; the question is whether that edge closed a
  lap ON PURPOSE. The one shape that says so is the continuous cycle: the
  refused node is the **entry** AND the last recorded step is **not bot
  work** (a `wait`, or the `notify` that ends a lap). Then the cap is the
  valve: the run ends `completed` with `error` =
  `execution cap of N bot steps reached before node "X"`, `currentNodeId`
  stays on the last finished step, the queue drains, and the operator is
  notified with kind `cap-reached` (index.ts maps it to a "finished"
  notification). Anything else — an edge back to the entry from a bot step
  (`code → test --retry--> code` two hundred times is not a finished run),
  or a path cut mid-way — ends `failed` with the same reason, `currentNodeId`
  on the refused node (a resume after raising the cap picks up there), and
  the usual failure notification. Both variants notify: hundreds of bot
  turns ending is an event to see, green or red. The timeline shows the
  completed variant as an "Ended:" note in warning tone. Old receipts
  carrying the old wording load unchanged.

**3b. Wait nodes honour the interval trigger's active window.** A lap that
loops inside one run never passes the trigger, so the trigger's window alone
would let bots deploy at 03:00. The persisted truth of a pause is
`waitStartedAt`; on every tick `sweepWaits` recomputes
`due = waitStartedAt + node.minutes` and `resume = nextActiveWindowStart
(current activeHours, max(due, now))` from the definition AS IT IS NOW —
`now`, not `due`, once the pause is over, so a tick that lands late (the
computer slept through 17:59) does not dispatch at 22:00 — advances when
`resume <= now`, and otherwise rewrites `waitUntil` (the instant the UI
shows) whenever it disagrees. So an edit mid-pause — window removed,
loosened, tightened, or the node's minutes changed — takes effect at the
next tick in either direction; `parkOnWait` only pre-fills the same value.
Only an `interval` schedule carries a window; a `daily`/`once` workflow's
waits are plain timers. A hand-edited window allowing no weekday fails the
run with a named reason rather than holding it forever. The receipt's
`startedAt` is `waitStartedAt`, and the summary says how long the run
actually waited.

**Weekday semantics of a window crossing midnight.** The weekday tested is
the one the INSTANT falls on: `22:00–06:00` on `[1]` (Monday) covers Monday
22:00–24:00 and Monday 00:00–06:00 — to cover the early hours of Tuesday,
list Tuesday too. The schedule editor says so under the day toggles.

**4. `cycle-without-wait` warning** in `validateWorkflow`: with every wait
node removed from the graph, if the entry can still reach itself along
routable edges, some lap has no pause in it. Warning on the entry node,
never an error; a cycle that does not pass through the entry (a review
loop) is silent, and so is an entry that is itself a wait node. Existing
fixtures with a self-loop on the entry now carry this warning alongside
`unwired-failure` (`server/index.test.ts` included).

**UI**: palette gets a Wait kind (`WORKFLOW_NODE_KINDS`, default 30 min),
card and panel render it, the run timeline says "Waiting until HH:MM ·
node", and the schedule editor gains an Interval mode with minutes, an
active-hours toggle, from/until times and weekday toggles; the workflows
list shows "Every N min · next run pending" while the clock is held.

### Recommended shape for the user's workflow

```
triagem ──(demanda)──▶ spec ──▶ … ──▶ doc ──▶ update-canal ──(sent)──▶ triagem
   │
   └──(nada)──▶ sem-demanda ──(done)──▶ wait(30) ──(elapsed)──▶ triagem
```

- `sem-demanda → wait(30) → triagem`: an empty triage sleeps half an hour
  and looks again. Without the wait the validator warns (`cycle-without-wait`).
- `update-canal → triagem`: a finished delivery goes straight back to
  triage — there may be more demand. `update-canal` is a notify, so a cap
  hit on that edge is the `completed` variant.
- Trigger: `interval`, 60 min, with `activeHours` for working hours. The
  window is honoured at both points where a lap can start: the trigger
  (first lap of a run) and every wait node (later laps). A lap already in
  flight at 18:00 runs to its end; the window is where laps START, not a
  kill switch.
- The run ends only at the execution cap (or on a failure); the trigger
  brings the workflow back one interval after the run ended, never while
  one is live.
- `maxNodeExecutions`: the user has 24, and wait/notify steps no longer
  count, so that is 24 bot turns. The cap ends a run `completed` only on
  the two loop-closing edges above; hit mid-lap it is a `failed` run that
  the interval trigger recovers from one interval later (with a failure
  notification each time). Two ways to keep it clean: raise the cap to a
  comfortable multiple of a lap (default now 200, up to 1000), or route
  `update-canal` to a sink so one delivery is one run and only the
  no-demand loop cycles inside a run.

### Left out

- No UI for `maxNodeExecutions` itself (still only settable through the
  API / JSON), as before.
- `activeHours` is evaluated in the app's local timezone; there is no
  per-workflow timezone. The window gates where laps START (trigger and
  wait nodes); it does not interrupt a lap in flight.
- The wait is a fixed pause. "Wait until HH:MM" or "wait for a webhook" are
  different nodes and were not built.
- The completed-at-cap receipt reuses the `error` field on the run rather
  than adding a new one, so older clients would show it in failure tone.
